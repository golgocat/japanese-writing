# 推敲の照合手順

既存の日本語を直すときに、直した案が原文と同じことを言っているかを確かめるための参照。推敲、情報・業務文の見直し、AIっぽさの除去、要約の見直しで使う。新規作成や翻訳でも、「原文照合」の段で文の種類と6点を使える。
考え方の一部は nanaism/yomiyasu（MIT）v2.0.0 を参考にした。文言と表は転載せず、このスキルの言葉で書いている。

## 1. 言い直しテスト

直すか残すかに迷う箇所ごとに、次の順で決める。

1. 直した案を1つ書く。
2. 原文と案を、下の6点で比べる。
3. 1つでも変わるなら、案を捨てて原文を残す。通るまで案を作り直さない。
4. すべて同じなら案を採る。

| 点 | 同じといえるとき | 変わる案の例（説明用の短文。元と案） |
| --- | --- | --- |
| 何について述べるか | 主題と論点が同じで、別の概念にすり替えていない | 元「設計の要は単純さにある」、案「設計のねらいは単純さだ」 |
| 何を認め、何を否定するか | 認めたことと否定したことが入れ替わらず、否定が消えも増えもしない | 元「手戻りがなくなったわけではない」、案「手戻りがなくなった」 |
| 誰が誰にするか | 動作主、相手、頼むのか説明するのかの向きが同じ | 元「田中さんが山本さんに確認を頼んだ」、案「田中さんが確認した」 |
| 範囲と条件 | 「一部」「〜の場合だけ」「〜まで」の限定と、掛かる動作が同じ | 元「管理者の場合だけ削除できる」、案「削除できる」 |
| 言い切りの強さ | 断定、推量、伝聞、可能の強さが同じ | 元「原因は設定の誤りとみられる」、案「原因は設定の誤りだ」 |
| 数値・固有名詞・時期 | 数、単位、名前、日付、「先月から」のような時期が同じ | 元「約30件の問い合わせ」、案「30件の問い合わせ」 |

- 語を言い換えただけで6点が同じなら、案を採る。
- 漢語や名詞化に置き換えた案は、6点が同じでも硬くなりやすい。和語の短い言い方で書けるなら、そちらを選ぶ。
- 文や語句を削る案は、6点を比べる代わりに、削る部分にしかない主張・条件・数値・期限がないかを見る。あれば削らずに残すか、同じ意味で本文へ移す。
- 否定の言い回しは、誰かの思い込みや外れた仮説を正していることがある。Aを消してBだけを言う案が原文と同じ主張になるかを比べ、変わるなら残す。消したAが「目的」「優先」の側に移っていないかも確かめる。
- 残した箇所には、残した理由を報告に1行書く。

## 2. 文の種類

書き直す前に、各文の種類を把握する。直したあとに、原文と読み比べて種類が変わっていないかを確かめる。

| 種類 | 例 | 変わりやすい直し |
| --- | --- | --- |
| 事実 | 会議は10月9日に開かれた。 | 日付や主体が抜ける |
| 意見・評価 | 手順が分かりにくいと感じた。 | 「感じた」を外して事実の文にする |
| 依頼・決まり | 10月9日までにご確認ください。 | 依頼を「確認する」という決定や実施済みにする |
| 例え・比喩 | 半日が消えた。 | 比喩を事実に直すとき、原因や結果を足す |
| 皮肉・冗談・反語 | 誰が読むというのでしょう。 | 反語を単なる疑問や断定に変える |
| 仮定・予測 | 遅れる可能性がある。 | 予測を事実や約束にする |
| 引用・伝聞 | 担当者によると、来週に延びる。 | 伝聞を書き手の断定にする。引用の中身を直す |

- 決めきれない文は、候補のまま扱う。どちらの種類に読めても成り立つように、そのままにするか、読みを決めない形で直す。
- 書き手がわざと複数の読みを残した箇所は、一つに決めない。含みのある言い方、二重の意味、読み手に委ねる余白は直さない。
- 種類が変わる案は、1章の6点の「言い切りの強さ」か「何を認め、何を否定するか」が変わっているので捨てる。

## 3. ぼかした所の補いと問い

ぼかした所とは、指す先が見えない語（「あの件」「先日」）、抜けた主語、数値、条件、単位。補うのは、次のすべてを満たすときだけ。迷ったら補わない。

1. 同じことを述べた文が、原文、依頼、資料、会話の利用者の発言のどれかにある。値が合うだけでは足りず、対象、条件、時点が同じ文であること。
2. 根拠の範囲が、原文の文より狭くない。狭ければ補わずに尋ねる。
3. 言い切りの強さを変えずに書ける。「予定」「かもしれない」はそのままにする。
4. 書き手が意図してぼかしたのではない。そう思えるときは補わない。
5. 主体を補うのは、根拠の文でその人が同じ動作の主語であるときだけ。報告した人を、作業した人や担当にしない。

- 根拠に使わないもの: 自分や別のAIの出力、自分で書いた下書き、要約した文。
- 補った箇所は、報告で「元と後」と根拠の文を並べる。補うのは1回の依頼で5件まで。
- 補えない所は足さない。元の書き手に渡せる短い問いにまとめる。問いは最大3つで、1つの問いに穴を1つだけ入れ、答えが短く済む形にする。
- 穴ではないもの: 「未定」「調査中」、わざとのぼかした数や相手、要約で省いた細部、結びの決意。補わず、問いも出さない。
- 材料どうしが食い違うときは、どちらかに決めず、両方を並べて尋ねる。
- 公開する文に〇〇や【要確認】のような仮置きが残っているときは、埋めずに残っていることを報告する。根拠があれば上の条件で補う。

## 4. 変更報告

- 変更を報告するときは、元の表現と直した後の表現を先に見せる。そのあとに理由を1行で添える。
- 構成は次のとおり。
  - 変えたところ: 元、後、理由。
  - 残したところ: 表現と、直すと変わってしまう点。
  - 補ったところ: 元、後、根拠の文。
  - 確認したいこと: 3つまでの短い問い。
- 案を捨てて残した箇所を「変えたところ」に書かない。直していない箇所を直したと書かない。
- 点数、検査の件数、「読みやすくなった割合」のような数字を、直した根拠にしない。数字が出せるのは、利用者が指定した字数など、依頼の制約を実測したときだけ。
- 本文のみの指定があるときは、報告を付けない（Output contract が優先）。

## 5. 補助ツールの扱い

- yomiyasu の lint と diff は、規則に当たった箇所と、数値、否定、確度の変化を拾う補助として使える。意味が保たれたことと、読みやすさの合格は判定しない。
- 出た候補は読んで採否を決める。誤検知を判断せずに採用しない。点数で合否を決めない。
- 自動実行、フック、CIへの組み込みは、このスキルの手順に入れない。
