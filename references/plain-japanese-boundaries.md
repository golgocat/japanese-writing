# 演出過多の日本語：境界例

情報・業務文書の執筆・監査で、`SKILL.md` の Target quality と併用する。語の一律禁止ではなく、その文脈で具体的な意味を担うかを判定する。

改善例に含まれるサービス内容・日時・対象は、その文書の資料に根拠がある場合だけ使う。抽象的な原文だけから具体的な情報を作らない。

演出過多かどうかと、語の選択が適切かどうかは別に確認する。仕様では技術的な関係を明確な用語で示し、生活者向け広告では普段使う呼び方を選ぶ。

## 表現を見直す基準

1. 対象、動作、因果、差分、担当、期限を具体的に伝えているか。
2. 平易な語へ戻しても必要な意味や礼節が減らないか。
3. 抽象的な比喩を解読せず、初見で同じ内容を理解できるか。
4. 表現の強さが用途と依頼に合うか。

形式的な語の禁止表にはしない。実際の提出先を示す「総務へ」、状態遷移を示す「旧環境から新環境へ」はそのまま使える。
対人文の感謝や弔意、指定された創作の余韻は、情報量だけで不要と判断しない。

## 書き直す例

| 用途 | 演出過多 | 普通の日本語 | 判断理由 |
|---|---|---|---|
| スライド章名 | まず、物件の使い方とホテル名を決める | 物件概要とホテル名のアイデア | 章の内容を示すだけで足り、進行の演出は不要 |
| スライド章名 | 清掃・受付・現地対応・設備を一つの運営体制に | 運営体制（清掃・受付・現地対応・設備） | 統合行為ではなく、扱う項目の一覧 |
| スライド章名 | 予約システムを中心に、予約から入室・会計までをつなぐ | 予約システムによる予約・入室・会計連携 | 製品名と連携対象を直接示せる |
| 比較見出し | 同じ売上条件で、運営費とオーナー手残りを比べる | 運営費とオーナー手残りの比較（同一売上条件） | 比較軸と前提を短く特定できる |
| 報告書 | 現場の声を未来のサービスへつなぐ | 利用者の要望を次期仕様に反映する | 入力と処理結果を具体化できる |
| 製品説明 | 予約体験のその先へ | チェックアウト後の荷物預かり | 提供内容を抽象的な方向表現で隠している |
| 提案書 | 利益を最大化する運営へ | 運営費の削減案 | 達成条件のない最大化表現を避ける |
| メール件名 | 新たな一歩へ向けたご相談 | 10月の店舗移転に関するご相談 | 用件を直接特定できる |

## そのまま使える例

| 表現 | 許容理由 |
|---|---|
| 請求書を9月18日までに経理へ送付してください。 | 宛先、行動、期限が明確 |
| 旧予約システムから新しい予約システムへ10月1日に移行する。 | 起点、移行先、日付が実在する状態遷移 |
| 予約システムと会計システムをAPIで接続する。 | 仕様に合う用語で接続対象と方法を明示 |
| 自社運営は委託運営より月間運営費が82万円低い。 | 根拠確認済みなら、見出しに値する直接的な結論 |
| 添付した見積書をご確認ください。 | メールに必要な自然な依頼 |
| エアコンでこわばった身体を、じっくり伸ばす。 | 広告で日常的な呼び方を使い、商品との関係と身体動作が事実に沿う場合 |
| 街と人の未来をつなぐ | 企業紹介のブランドメッセージとして意図された文脈なら許容。通常の事業説明見出しなら具体化する |
| 朝の光が、まだ名前のない一日をひらく。 | 詩的な文章を明示的に求められた創作なら許容 |

## 前方検証用の境界課題

新しいルールを変更したときは、少なくとも次の用途で結果を確認する。

1. **スライド**：章名は内容ラベルへ戻す一方、数値で示せる結論見出しは文のまま残るか。
2. **報告書**：抽象的な総括を具体化しつつ、因果関係を示す動詞を失っていないか。
3. **通常メール**：スローガン調の件名を避けつつ、依頼、期限、礼節を残せるか。
4. **製品仕様**：`APIでつなぐ` を `APIで接続する` に直し、接続・遷移の意味を保持できるか。ブランド表現の `つなぐ` まで一律に置き換えていないか。
5. **広告**：ストレッチ広告では `冷房` より `エアコン` を選びつつ、具体的な便益や感覚表現を残せるか。設備仕様の `冷房能力` などは保持できるか。
6. **創作**：詩的表現を明示された依頼では、情報文書の既定を過剰適用していないか。

7. **技術メモ**：比喩動詞を操作や状態へ戻しつつ、機器故障などの字義どおりの用法は残すか。
8. **報告書**：無生物主語を人・組織・事実へ戻しつつ、「結果は〜を示している」は残すか。原文にない担当や対策を足していないか。
9. **創作**：依頼された比喩を、情報文書の既定で消していないか。

判定が割れる場合は、単語ではなく、用途、文字数、読み手、根拠、直前直後の具体性を確認する。

## 統語の復元と比喩・空洞語・表記

情報・業務文で、1文の動作関係と、意味を担わない演出を見直す。語の一律禁止ではない。創作・広告の依頼、字義どおりの用法、利用者が指定した書式は残す。

原文にない主体、効果、数値、原因は足さない。不明なら中立のままにするか、利用者に確認する。主体不明の受動態は、推測で能動態にしない。

### 規則

1. **誰が・何を・どうした**：1文ごとに動作主・対象・動作を復元する。曖昧な「これ」「片方」「両者」は直前の具体名詞へ戻し、主語を述語の近くに置く。動作主が不明なら述べない。
2. **比喩動詞**：情報・業務文でAIが多用する「効く」「壊れる」「倒す（〜側に倒す）」「溶かす」「潰す」「踏み込む」「黙って〜／静かに〜」は、具体の操作や状態変化へ戻す。創作・広告の依頼や、機器が壊れる等の字義どおりの用法は残す。「静かに壊れる」が無言の失敗を指すなら、エラーや警告の有無を原文の意味に合わせて書く。失敗の仕方や原因が不明なら確認し、補作しない。
3. **無生物主語**：概念・道具・事例が「導く／残す／語る／要求する」のように意志を持つかに読める文は、人・組織・システムの行為か、観測できる事実へ戻す。学術の「結果は〜を示している」は残してよい。
4. **前置きと否定対比**：「重要なのは」「結論から言うと」「正直に言うと」は削り、要点から書く。誰も主張していない「XではなくY」はYだけ書く。ありそうな誤解を正す否定は残す。否定の範囲は変えない。
5. **空洞語**：情報・業務文の「解像度を上げる」「腹落ち」「温度感」「肌感」「本質的」は、実際に調べたこと・決めたことへ戻す。分からなければ確認し、具体を創作しない。
6. **表記**：日本語本文にダッシュ（— ―）を使わない。和欧文の間に半角空白を入れない（「READMEはyomiyasuで」）。同じ内容を言い換えるだけのカッコは外す。指定された項目名のコロン、コード、URL、識別子は変えない。

### 採用しないもの

箇条書きの一律な地の文化、文末をわざとばらすこと、平均文長の強制、利用者が指定した書式の上書きは採用しない。

### 前後の例

| 見直す点 | 原文・文脈 | 編集結果・判断 |
|---|---|---|
| 指示語 | 技術メモ。直前で承認フローと通知フローを対比。「これを片方に寄せると、両者が曖昧になる。」寄せ先は未記載。 | 承認フローと通知フローのうち、一方に寄せると、両方が曖昧になる。これ・片方・両者を直前の名詞へ戻す。寄せ先は推測しない。 |
| 比喩動詞 | 技術メモ「原因調査に半日溶かした。」 | 原因調査に半日かかった。所要だけを具体化し、原因や結果は補わない。 |
| 比喩動詞 | 技術メモ「未確認の変更は、入れない側に倒す。」 | 未確認の変更は入れない。「倒す」を削り、原文にある入れないだけを残す。 |
| 擬人化 | 報告書「この事例が運用チームに再発防止を求めた。」 | この事例について、運用チームへ再発防止が求められた。誰が求めたかは原文にないので述べない。 |
| 前置き | 社内連絡「結論から言うと、費用は未定です。」 | 費用は未定です。 |
| 不要な否定対比 | 障害連絡。進捗完了の主張はない。「進捗報告ではなく、障害報告です。」 | 障害報告です。 |
| 否定を残す | 試験報告「全件完了ではなく、3件は未確認です。」 | 保持。部分否定と3件を変えない。全件未確認にしない。 |
| 空洞語 | 報告書「要件の解像度を上げ、関係者の腹落ちを得た。」調査範囲と合意内容は未記載。 | 何を調べ、何を決めたかを確認する。解像度・腹落ちから項目や決定を補作しない。 |
| 和欧文空白 | 技術メモ「この README は API の使い方を示す。」 | このREADMEはAPIの使い方を示す。 |
| 重複カッコ | 手順「再起動（リスタート）する。」 | 再起動する。同じ意味の言い換えは外す。 |
| ダッシュ | 技術メモ。認証と期限切れの間にダッシュ記号があり、「先に直す」と続く。 | 認証と期限切れを先に直す。日本語本文にダッシュを使わない。 |
| 字義どおり | 障害報告「冷却ファンが壊れた。」 | 保持。機器の故障を指す。 |
| 創作の比喩 | キャッチコピー依頼「夜の雨が、看板の文字を溶かす。」 | 保持。依頼された比喩。 |

## 自然さと意味保持の追加例

| 見直す点 | 原文・文脈 | 編集結果・判断 |
|---|---|---|
| 技術用語 | 仕様：予約システムと会計システムをAPIでつなぐ。 | 予約システムと会計システムをAPIで接続する。「つなぐ」が比喩でなくても、仕様では「接続する」が適切 |
| 日常的な呼び方 | ストレッチ広告：冷房でこわばった身体を、じっくり伸ばす。 | エアコンでこわばった身体を、じっくり伸ばす。設備仕様の「冷房能力」は置き換えない |
| 冗長な動詞 | 申込内容の確認を行います。 | 申込内容を確認します。 |
| 可能表現 | 予約を変更することができます。 | 予約を変更できます。「変更します」では意味が変わる |
| 否定の範囲 | システムが停止しないとは限りません。 | システムが停止する可能性があります。「停止しません」にはしない |
| 確信度 | 遅延の原因は通信障害の可能性があります。 | 通信障害で遅延した可能性があります。原因の断定はしない |
| 条件と依頼 | 見積額が予算を超える場合に限り再見積もりを依頼してください。 | 条件付きの依頼として保持。無条件の依頼へ短縮しない |
| 主語と述語 | 返答が遅れた理由は、担当者が不在でした。 | 返答が遅れたのは、担当者が不在だったためです。 |
| 修飾関係 | 管理者が昨日更新した料金表を確認しました。 | 誰がいつ何を更新・確認したか曖昧なら、前後を確認してから直す |
| 受動態 | 書類が廃棄されました。 | 行為者不明なら保持。「担当者が廃棄しました」と補わない |
| 表現の反復 | 1. 画面を開きます。2. 日付を選びます。3. 保存します。 | 手順の文型は揃えたままにする |
| 情報不足 | この機能で作業時間を大幅に短縮できます。 | 根拠にない割合や時間を追加しない。効果の根拠を確認する |

## 公開資料から参考にした考え方

既存版には2026-09-15に元資料を確認した記録がある。以下は編集原則の参考であり、各スキルの自動導入・実行を指示するものではない。今回の再確認範囲は [research-sources.md](research-sources.md) に記載する。

- [natural-japanese：改稿手順](https://github.com/coji/natural-japanese/blob/main/skills/natural-japanese/references/revision-guide.md)：部分ごとに変更の必要性を判断し、仕上げに通読する。見出しの結論化や文型の回数制限は採用しない。
- [japanese-humanizer](https://github.com/geonwoo-jeong/japanese-humanizer/blob/main/plugins/japanese-humanizer/skills/japanese-humanizer/SKILL.md)：条件・否定・責任主体を守った局所修正。出自判定や根拠のないスコアは使わない。
- [textlintの技術文書ガイド](https://github.com/textlint-ja/textlint-rule-preset-ai-writing/blob/main/docs/tech-writing-guidelines.md)：具体的な動詞と用語統一。可能表現や義務表現は意味を確認して短くする。
- [文化庁「公用文作成の考え方」](https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93651301_01.pdf)：読み手に合う用語、正確さと分かりやすさの両立。公用文固有の表記規則は一律に適用しない。
- [meiseki](https://github.com/bamboo-nova/meiseki)：否定・条件の入れ子と名詞の連鎖を見直す。真偽を照合し、スコア低下を必須の合格条件にはしない。
- [ja-ai-polish](https://github.com/BrambleXu/ja-ai-polish)：書き換え前後の事実・条件・約束を照合する。文体見本は語調の参考にし、そこにある体験や主張を転載しない。
- [yomiyasu](https://github.com/nanaism/yomiyasu)：1文の「誰が・何を・どうした」の復元、情報文での比喩動詞と無生物主語の具体化、前置きと空洞語の削減、ダッシュ・和欧文間空白・重複カッコの整理。文言や表は転載しない。箇条書きの一律地の文化、文末のばらつき、平均文長の強制、指定書式の上書きは採用しない。
