# 広告・SNS・UX・創作

広告、LP、画像バナー、SNS、製品内の文言、創作を扱う場合に読む。
以下は本スキルの運用指針。外部団体の規格や効果が実証された広告手法として扱わない。

## 用途を分ける

媒体だけでモードを決めない。同じSNSでも、障害告知は情報文、キャンペーンは広告、詩は創作になる。
広告の便益やリズムを通常の報告・説明へ自動的に持ち込まない。
創作の依頼では表現性を尊重し、通常文の基準で比喩を一律に除去しない。
原文の語調を保持する指定があれば、目的に合う範囲でその語調を保つ。

## 広告・販促

- 読者、伝える価値、根拠、次の行動を先に決める。
- 機能だけでなく、顧客にとっての具体的な意味を伝える。
- 一つのセクション、一つの広告では、一つの主張を中心にする。
- 実際のレビュー、インタビュー、問い合わせにある顧客の言葉を参考にする。
- 顧客の言葉として使うために、架空のレビューや体験談を作らない。
- 温度、重さ、こわばり、手触り、動きなどは、商品と関係し、裏付けがある範囲で具体的に書ける。
- 数字、資格、実績、価格、期限、比較、効果は検証できる場合だけ使う。
- 可能性、対象者、期間、条件を削り、主張を強くしない。
- 「初回無料」「最大20%」「対象プラン」など、主張を限定する条件はその主張の近くに置く。別の行やCTAだけを読めば条件が分かる状態に頼らない。
- 不安を必要以上に煽らず、問題を示したら解決策へ早く進む。
- CTAは行動と得られるものを示し、実際の遷移先や処理に合わせる。
- 内部では便益、共感、具体性、使用場面、対比を比較し、目的に最も合う案を先に提示する。
- 候補を複数求められた場合も、語尾だけを変えず、訴求の違いを示す。

例: 検証済みの機能が「予約履歴から前回と同じメニューを選べる」の場合。
`予約履歴から、前回のメニューを選べます。`は具体的な便益を示す。
実測なしで`予約時間を半減`や`もう迷わない`と効果を断定しない。

## 用語の境界

- 生活場面では、読み手が普段使う具体的な呼び方を優先する。
- ストレッチ広告では`冷房でこわばった身体`より`エアコンでこわばった身体`を優先する。
- ただし、この語の選択自体を症状の原因や施術効果の根拠にはしない。
- 設備仕様の`冷房能力`など、機能や運転状態を指す用語は置き換えない。
- 技術仕様では`APIでつなぐ`より`APIで接続する`、短い見出しなら`API接続`を使う。
- 接続・連携・同期の意味を混同しない。平易にするために技術上の関係をぼかさない。
- `つなぐ`という語自体は禁止しない。広告や創作で具体的な意味と用途がある場合は判断する。

## 画像バナー

既定の出力は次の4要素だけにする。

1. カテゴリ: 任意の短いラベル。前に飾りの短い横線を置かない（em dashに見えるため）。
2. 見出し: 2行以内、一つの便益または意味。
3. 補足: 根拠または仕組みを1行。
4. CTA: 行動を1行。

説明段落、三つのベネフィット、重複スローガンは、明示要求がない限り加えない。
文字量はデザインへ渡す前に削り、実際のレイアウトで収まるか確認する。字数と文字サイズの上限は[readable-length.md](readable-length.md)を使う。
原稿上の改行だけで、すべての画面幅での行数や可読性を保証しない。
根拠がない場合、補足欄を埋めるための数値・実績・仕組みを捏造しない。
事実と用途に合えば、`具体的な実感 + 具体的な動作`や`生活場面 + 必要な時間`を使える。
この構造を情報・業務文書の見出しへ一律に転用しない。

## 構成の選び方

- バナー: `便益 → 理由 → 行動`。
- 短い広告文: `状況・悩み → 提案 → 根拠 → 行動`。
- LP: `問題 → 解決 → 便益 → 根拠 → 反論処理 → 行動`。
- 長文セールス: 必要に応じてPASBECONAなどを使える。

構成は必要な説明を整理する補助。要素を埋めるために架空の証拠、煽り、反論を作らない。
読者が既に理解している問題を長く語るより、判断に必要な情報を先に出す。

## SNS

- 投稿の目的が告知、説明、対話、販促、創作のどれかを決める。
- 日付、対象、条件、状況、次の行動が必要な場合は明示する。
- 文字数を減らすときは重複から削り、重要な留保や価格条件を落とさない。
- ハッシュタグ、絵文字、感嘆符、煽る疑問形は自動追加しない。
- 連続投稿にする場合は、主張と重要な条件を離しすぎない。
- 媒体の文字数や表示仕様は必要時に現在値を確認し、固定の暗記値で保証しない。読みやすさの上限は[readable-length.md](readable-length.md)を使う。
- 投稿原稿の作成と、実際の投稿・予約・返信は別の操作。文章の完成を送信承認とみなさない。

例: `一部の利用者でログインできません。復旧時刻は未定です。`
この告知を`もうすぐ快適なログイン体験を！`に変えない。
未定という状態、一部という範囲を保ち、確認できた次の案内があれば添える。

## UX・操作ラベル

- ラベルは動作と対象を短く示す。短縮より、操作結果の正確さを優先する。
- `保存`、`送信`、`購入`、`削除`を一律に`続ける`へ丸めない。
- 確認画面へ進む操作と、処理を確定する操作を区別する。
- 同じ操作は同じ用語で呼び、本文とボタンの意味を一致させる。
- リンク先や設定名は、実際の名称と対応させる。
- 操作対象を色、位置、絵文字だけで示さず、名前でも特定できるようにする。
- 入力例は要件を明確にするために使い、実在者の個人情報を例として作り込まない。

| 操作 | ラベル例 | 避ける表現 |
|---|---|---|
| 予約内容を確認する画面へ進む | 予約内容を確認 | 予約を確定、予約完了 |
| 下書きを保存する | 下書きを保存 | 送信、公開 |
| 選択したファイルを削除する | ファイルを削除 | 整理する |

## エラー・状態表示

- 確認済みの問題と、可能な次の行動を示す。
- 原因が不明なら、通信環境や利用者の操作のせいと断定しない。
- 成功未確認で`保存しました`、処理中に`完了しました`と書かない。
- 再試行が安全な場合だけ、再試行を案内する。
- 決済など重複処理の可能性がある場面は、実際の確認・復旧手順に合わせる。
- エラーコードは問い合わせ等に必要なら残すが、コードだけで説明を済ませない。

例: 保存失敗が確認でき、再試行が安全なら`保存できませんでした。もう一度お試しください。`
通信原因が未確認のまま`インターネット接続を修正してください`とは決めつけない。

## 創作と事実

- 詩、物語、情緒的なブランド表現を明示的に求められた場合、比喩、余韻、感情、独自のリズムを使える。
- フィクションの登場人物の体験や感情を創作することと、実在者の経験を捏造することを区別する。
- 架空の利用者の声、未検証の実績、商品効果を、創作という理由で事実として掲載しない。
- 実在の事実が混じる創作では、依頼された事実の制約を保つ。
- `雨の匂いが、帰り道をほどく。`は詩では候補になる。障害報告の状況説明には使わない。
- 創作の評価では、比喩があること自体を不合格にせず、指定された目的と表現の働きで判断する。

## 最終確認

- 用途に合うモードで、主張と根拠が対応しているか。
- 数字、効果、体験、期限、条件を作ったり強めたりしていないか。
- CTAやラベルが、実際の操作結果を正しく示しているか。
- 通常文を広告調に変えたり、依頼された創作の表現性を一律に消したりしていないか。
